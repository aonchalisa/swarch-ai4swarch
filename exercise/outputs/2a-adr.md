# ADR-0002: แยกงานหลังสั่งซื้อด้วยเหตุการณ์ OrderPlaced

- **Status:** Proposed
- **Date:** 2026-10-27
- **Deciders:** ยังไม่ระบุผู้มีอำนาจตัดสินใจ

## Context and problem

ตาม requirement ในข้อความผู้ใช้ หลังสั่งซื้อระบบต้องส่งอีเมลผ่าน MailFast แทน logic จำลองของ `emailservice`, ให้แต้มผ่าน `loyaltyservice` ใหม่ และบันทึกเหตุการณ์ analytics ให้การตลาด โดยคาดว่าจะเพิ่ม SMS, fraud scoring และการอัปเดต recommendations ในปีหน้า

ต้องเลือกวิธีส่งต่องานเหล่านี้โดยรองรับการเพิ่มผู้รับงาน ข้อมูลเกี่ยวกับเส้นทาง checkout ปัจจุบัน การจัดเก็บคำสั่งซื้อ และข้อจำกัดการทำงานจริงเป็น **Not evidenced in the provided files** เนื่องจาก `context: none` จึงไม่ใช้ผลจาก Run ก่อนหรือ scenario เป็นหลักฐาน

## Decision drivers

ลำดับต่อไปนี้เป็นเกณฑ์ที่เสนอเพื่อพิจารณา มิใช่ข้อจำกัดที่ผู้ใช้ยืนยันแล้ว

- **Modifiability:** เพิ่มงานหลังสั่งซื้อโดยลดการแก้ไขผู้สร้างคำสั่งซื้อ สอดคล้องกับแผนขยายใน requirement
- **Reliability:** ป้องกันงานสูญหายและผลข้างเคียงซ้ำเมื่อส่งงานใหม่
- **Performance:** ลดการรอระบบปลายทางในเส้นทางตอบกลับการสั่งซื้อ
- **Operability และ cost:** ให้ทีมติดตาม retry และแก้ปัญหางานค้างได้ โดยประเมินต้นทุนระบบเพิ่มเติมก่อนยอมรับ

## Considered options

1. เรียก MailFast ผ่าน `emailservice`, `loyaltyservice` และตัวบันทึก analytics แบบ synchronous จากเส้นทางสั่งซื้อ
2. ส่งเหตุการณ์ `OrderPlaced` ผ่าน durable message broker แล้วแยกผู้ประมวลผลแต่ละงาน
3. บันทึกงานหลังสั่งซื้อในฐานข้อมูล แล้วให้ worker กลางสำรวจและดำเนินงานตามสถานะ

### Pros and cons of the options

| Option | Pros | Cons |
|---|---|---|
| 1 | ลำดับการทำงานตรงไปตรงมาและเห็นผลทันที; ไม่ต้องเพิ่ม broker | [Inferred] เวลาตอบกลับขึ้นกับปลายทาง; ต้องแก้เส้นทางสั่งซื้อเมื่อเพิ่มงาน; ต้องออกแบบกรณีสำเร็จบางส่วน |
| 2 | [Inferred] เพิ่มผู้รับเหตุการณ์ได้แยกจากผู้สร้างคำสั่งซื้อ; แยก retry และการประมวลผลแต่ละงาน | เพิ่ม broker และภาระดูแล; ผลลัพธ์เกิดภายหลัง; ต้องจัดการข้อความซ้ำและการเผยแพร่ที่ล้มเหลว |
| 3 | เก็บสถานะงานและ retry ในที่เดียว; ไม่ต้องเพิ่ม broker | [Inferred] polling เพิ่มภาระและเวลารอ; worker กลางอาจสะสม coupling; ต้องจัดการการแย่งงานและขยายกำลังประมวลผล |

## Decision

เสนอเลือกทางเลือก 2 เพื่อรองรับการเพิ่มงานหลังสั่งซื้อ โดยยังไม่เลือกผลิตภัณฑ์ broker เพราะไม่มีข้อมูลข้อจำกัดหรือความถนัดทีม การตัดสินใจนี้ต้องผ่านการตรวจสอบในหัวข้อ Validation ก่อนรับรอง

องค์ประกอบต่อไปนี้เป็นแบบที่เสนอ ไม่ใช่ข้ออ้างว่าระบบปัจจุบันมีองค์ประกอบดังกล่าวแล้ว

- สร้าง `OrderPlaced` หลังถึงจุดที่ธุรกิจนิยามว่าคำสั่งซื้อสำเร็จ ใช้ `event_id`, `order_id` และ `schema_version` พร้อมข้อมูลขั้นต่ำที่ผู้รับต้องใช้ ห้ามใส่ข้อมูลบัตรชำระเงิน
- ใช้ durable broker และช่องรับงานแยกสำหรับอีเมล แต้มสะสม และ analytics เพื่อให้แต่ละงานมีสถานะ retry อิสระ การส่งถึง broker ต้องรอการยืนยันก่อนทำเครื่องหมายว่าส่งสำเร็จ
- ปรับ `emailservice` ให้รับงานและเรียก MailFast; สร้าง `loyaltyservice` สำหรับแต้ม; สร้างผู้รับเหตุการณ์ analytics แยกต่างหาก โดยยังไม่สมมติ protocol ของ MailFast หรือที่เก็บ analytics
- ใช้การส่งแบบ at-least-once และออกแบบผู้รับให้ idempotent: งานแต้มต้องบันทึกกุญแจธุรกิจ เช่น `order_id` ร่วมกับการเพิ่มแต้มแบบ atomic; analytics ต้องตรวจซ้ำตาม event; อีเมลต้องใช้ idempotency key ของ MailFast หากรองรับ
- หาก MailFast ไม่รองรับ idempotency จะยังมีกรณีส่งอีเมลสำเร็จแต่บันทึกผลไม่ได้ ต้องตกลงวิธีตรวจสอบก่อน retry โดยไม่อ้างว่ารับประกัน exactly-once ได้
- เสนอ transactional outbox เพื่อบันทึกคำสั่งซื้อและเหตุการณ์ใน transaction เดียว แล้วส่งออกภายหลัง ทั้งนี้ต้องตรวจสอบก่อนว่าระบบมีการบันทึกคำสั่งซื้อและรองรับ transaction ดังกล่าว หากไม่มี ต้องออกแบบจุดบันทึกที่เชื่อถือได้และการกระทบยอดก่อนใช้งานจริง
- ยืนยันรับงานหลังบันทึกผลสำเร็จเท่านั้น ใช้ retry ที่มี backoff และขีดจำกัดตามนโยบายที่ต้องตกลง แยกงานที่ล้มเหลวซ้ำไปยังพื้นที่ตรวจสอบและรองรับ replay

## Consequences

- **Positive:** [Inferred] เพิ่มผู้รับเหตุการณ์สำหรับงานใหม่ได้โดยลดการเปลี่ยนเส้นทางสั่งซื้อ (quality attribute: modifiability)
- **Positive:** [Inferred] การประมวลผลปลายทางภายหลังช่วยลดเวลาที่ checkout ต้องรอ และแยกความล้มเหลวของผู้รับแต่ละราย หากมี outbox ที่เชื่อถือได้ (quality attributes: performance, availability)
- **Negative:** ผลอีเมล แต้ม และ analytics ไม่พร้อมพร้อมกัน ต้องสื่อสารสถานะที่อาจล่าช้า (quality attribute: consistency)
- **Negative:** เพิ่ม broker, worker, outbox relay และการติดตามงานค้าง (quality attributes: operability, cost)
- **Risks and mitigations:** การบันทึกคำสั่งซื้อสำเร็จแต่ไม่ส่งเหตุการณ์อาจทำให้งานสูญหาย; ตรวจสอบ atomic outbox และการกระทบยอดก่อนใช้งาน (quality attribute: reliability)
- **Risks and mitigations:** ข้อความซ้ำอาจทำให้แต้มซ้ำหรือส่งอีเมลซ้ำ; ใช้ atomic deduplication และตรวจความสามารถ MailFast โดยเฉพาะช่วงล่มหลังทำผลข้างเคียง (quality attribute: correctness)
- **Risks and mitigations:** งานค้างหรือข้อความเสียอาจหยุดงานบางประเภท; แยกช่องรับงาน ติดตามอายุงาน กำหนด retry และกระบวนการ replay (quality attributes: availability, operability)
- **Risks and mitigations:** เหตุการณ์อาจมีข้อมูลส่วนบุคคล; จำกัดข้อมูล สิทธิ์ผู้รับ และระยะเก็บตามนโยบายที่ต้องยืนยัน (quality attribute: security)

## Validation

- ตรวจเส้นทางสั่งซื้อและขอบเขต transaction เพื่อพิสูจน์ว่าทุกคำสั่งซื้อที่สำเร็จมีงานที่กู้คืนได้; ทดสอบการล่มระหว่าง commit, publish และการยืนยันรับงาน
- ทดสอบปิด MailFast, ผู้รับแต้ม, analytics และ broker แยกกัน ตรวจการสะสมงาน การกู้คืน และผลต่อการสั่งซื้อตามนโยบายความล้มเหลวที่ธุรกิจอนุมัติ
- ส่งเหตุการณ์ซ้ำและทำให้ผู้รับล่มหลังบันทึกผลแต่ก่อนยืนยันรับ ตรวจว่าแต้มไม่เพิ่มซ้ำ และตรวจข้อจำกัดการป้องกันอีเมลซ้ำกับ MailFast
- วัด checkout latency, เวลาจากสั่งซื้อถึงผลของแต่ละงาน, throughput, backlog และอัตราความล้มเหลว เทียบเกณฑ์ที่ต้องตกลงก่อนทดสอบ โดยไม่กำหนดตัวเลขเอง
- ทดลองเพิ่มผู้รับงานจำลองอีกหนึ่งประเภท และตรวจว่าไม่ต้องเปลี่ยน logic สั่งซื้อเมื่อสัญญาเหตุการณ์ยังเพียงพอ

## Open questions

- ใครเป็นผู้ตัดสินใจ และงานใดต้องสำเร็จก่อนตอบกลับว่าคำสั่งซื้อสำเร็จ? ยอมรับความล่าช้าและความล้มเหลวของแต่ละงานได้เพียงใด?
- เป้าหมาย checkout latency, ปริมาณคำสั่งซื้อช่วงพีก และเส้นตายอีเมล แต้ม และ analytics คือเท่าใด?
- ปัจจุบันบันทึกคำสั่งซื้อที่ใด และทำ transaction ร่วมกับ outbox ได้หรือไม่? หากบันทึกงานไม่ได้ จะตอบกลับการสั่งซื้ออย่างไร?
- MailFast ใช้ API/protocol ใด มี rate limit, timeout, SLA, idempotency และวิธีค้นผลการส่งอย่างไร?
- กฎการให้แต้ม การยกเลิกหรือคืนเงิน และกุญแจป้องกันแต้มซ้ำคืออะไร?
- analytics ต้องส่งไปที่ใด ต้องเรียงลำดับหรือเก็บย้อนหลังหรือไม่ และต้องมีข้อมูลใดบ้าง?
- ทีมมีทักษะ งบประมาณ ข้อกำหนด deployment และความสามารถดูแล broker/worker แบบใด?
- ต้องเก็บเหตุการณ์และข้อมูล deduplication นานเท่าใด ใครดูแลงานค้างและอนุมัติ replay?
